### Loader eligibility gate

A candidate loader is “available and compatible” for Jammarr only after it proves all of the following:

- Every dependency, mapping, plugin, loader, and API resolves from a pinned immutable coordinate or a retained checksum-verified archive.
- CI can reproduce the release artifact without a developer workstation, pre-modified Minecraft JAR, mutable snapshot, or undisclosed local cache.
- A real client and dedicated server launch on the declared Java runtime, unless the target is explicitly classified as a client companion.
- The target exposes the lifecycle, tick, custom-payload, keybind, screen, configuration, command, persistence, and audio hooks needed by the parity contract.
- A bounded bidirectional Jammarr hello and payload round trip succeeds before the full port begins.
- The release JAR can be distributed legally without bundling Minecraft, proprietary mappings, or loader components whose terms prohibit redistribution.
- CurseForge, Modrinth, and GitHub publication metadata can describe the artifact accurately. If a platform lacks the loader or Beta game-version taxonomy, GitHub becomes the authoritative download rather than assigning a misleading loader tag.
- The complete runtime and audible-output acceptance gates pass. Compilation, remapping, title-screen launch, or packet receipt alone is insufficient.

Failed experiments must remain harmlessly unadvertised: remove partial runtime claims, retain a concise feasibility result, and do not count the target in release totals.

### Legacy adapter architecture

Refactor the current Forge 1.7.10 implementation into reusable legacy services plus thin version/loader adapters instead of cloning its source tree repeatedly:

- `LegacyClientBridge`: lifecycle, connection state, key registration, screen opening, sound reload, and client-thread dispatch.
- `LegacyServerBridge`: tick dispatch, player capability state, operator checks, world/server storage paths, and clean shutdown.
- `LegacyNetworkBridge`: vanilla custom-payload framing, loader registration, protocol-6 hello, negotiated limits, and disconnect cleanup.
- `LegacySavedDataBridge`: schema-4 persistence with an explicit stable `markChanged` contract so MCP/SRG/intermediary naming cannot recreate the 1.7.10 `markDirty()` linkage failure.
- `LegacyCommandBridge`: public status, operator-only diagnostics/control, console/RCON handling, and exact redaction.
- `LegacyScreenBridge`: the same player tabs, separate Adventure tab, search-field preservation, tooltips, configuration UI, translated labels, and Controls entry using each era's widgets.
- `LegacyAudioBridge`: streaming MP3 decode and PCM submission through Minecraft's existing LWJGL/OpenAL context without creating a second context.

Keep the shared Plex, queue, station generation, Sonic Adventure pathing, cache, protocol, timing, transfer, and coordinator behavior in the Java-8-compatible core. Loader adapters must not contact Plex or acquire credentials on the client.

For LiteLoader, prefer the same bounded vanilla custom-payload transport used by the full legacy targets. If LiteLoader remains client-only, record its supported pairing explicitly, such as `1.8.9 LiteLoader client -> 1.8.9 Forge server`, and test that pairing directly. Do not weaken protocol validation or accept cross-Minecraft connections to make the pairing work.

### Feature-parity contract

Every full legacy target must implement the existing 1.1.0 behavior unless an exception is both technically unavoidable and documented in the generated manifest:

- Server-only Plex address, token, selected-library enforcement, secret redaction, and fail-closed configuration.
- Library discovery, browse/search pagination, bounded error/timeout states, and no indefinitely searching Queue tab.
- Queue display, add, play, pause, skip, clear, and reorder operations.
- General stations plus the separate **Adventure** tab and Sonic Adventure waypoint generation.
- Endless autoplay transitions, recent-track exclusion, cache-backed outage playback, and transcode normalization.
- Late join, reconnect, sound reload, underrun recovery, drift correction, and final retry behavior.
- Local mute/volume, status, redacted diagnostics, persistence/migration, and optional-client negotiation.
- A translated player/menu key in Controls, translated screen/config options, the default `J` binding, and an automated key-conflict check against the target's vanilla controls.

Loader conveniences may differ: Mod Menu integration is optional where no equivalent exists, clickable chat may fall back to plain text, and a LiteLoader companion may delegate server configuration/commands to its paired server. Core music, queue, station, Adventure, synchronization, and security behavior may not silently disappear.

## Implementation plan

### 1. Establish the 1.1.0 baseline

- Bump the mod to 1.1.0 because this is a substantial compatibility feature, not another 1.0.2 patch adjustment.
- Preserve saved-data schema 4 unless porting exposes a real persistence change.
- Bump the network protocol from 5 to 6.
- Add feature flags and negotiated transport limits to the hello packets so future capabilities can evolve without another all-or-nothing rewrite.
- Record all 26 Minecraft targets in one machine-readable target manifest.

### 2. Make client installation optional

Introduce a shared capability registry with states such as `UNKNOWN`, `CAPABLE`, `ABSENT`, and `INCOMPATIBLE`.

- A player becomes `CAPABLE` only after a valid protocol-6 hello.
- Missing clients remain connected and receive no Jammarr payloads.
- Missing-client timeout changes from “disconnect” to “classify as absent.”
- A late valid hello may activate Jammarr during the same connection.
- Clients actively advertising an incompatible Jammarr protocol still receive a clear rejection.
- Disconnects remove capability, transfer, rate-limit, and listener state atomically.
- Broadcasts, manifests, audio chunks, station state, and diagnostic responses iterate only over negotiated listeners.
- `pauseWhenEmpty` should count Jammarr-capable listeners, because vanilla players cannot hear the stream.
- Unmodded players must not control Jammarr through commands. Modern command trees should be resent after capability negotiation; handlers must independently reject non-capable players.
- Server console and RCON administration remain functional.

Loader-specific work:

- Forge 1.7.10/1.12.2: accept missing remote mod metadata, stop kicking on missing hello, and never use the SimpleNetworkWrapper channel before capability confirmation.
- Modern Forge: accept `ABSENT` and `ACCEPTVANILLA` while requiring the exact protocol when the channel exists, following Forge’s [optional-channel guidance](https://docs.minecraftforge.net/en/1.19.x/networking/simpleimpl/).
- NeoForge: register payloads through `PayloadRegistrar.optional()` and check negotiated availability before sending.
- Fabric/Quilt: use `ServerPlayNetworking.canSend` plus the application hello before activating the listener.
- A modded client connecting to a server without Jammarr should also remain connected; its key/menu should report that the server does not support Jammarr instead of sending an unsupported packet.

### 3. Harden transport and resource use

- Replace immediate multi-chunk sends with a fair server-tick egress scheduler.
- Apply per-player and global byte/chunk budgets so one lagging client cannot monopolize the server thread.
- Keep strict request sequencing, acknowledgement, playback-lead, and buffer limits.
- Reject all control and chunk traffic from clients that have not completed negotiation.
- Add bounded queues to the three-thread Plex/cache executor; coalesce redundant validation, generation, browse, and prefetch jobs.
- Add lifecycle generations/cancellation so async completions cannot mutate a stopped server or superseded track.
- Replace whole-track `Files.readAllBytes` caching with file-backed frame offsets and bounded chunk reads.
- Cap accepted transcode size, duration, chunk count, and temporary-disk use before indexing.
- Preserve atomic cache installation and remove partial files on every failure or shutdown.
- Extend diagnostics with capable/vanilla listener counts, queued work, egress backlog, cache memory, rejected requests, and underruns without exposing Plex credentials.

### 4. Normalize the build layout

Before creating dozens of copied builds:

- Move the root 1.21.1 NeoForge implementation into the same `platforms/<mc>/<loader>` structure as every other target.
- Generate root verification tasks, release manifests, filenames, Java toolchains, and dependency locks from the target manifest.
- Separate build-JDK, runtime-JDK, and bytecode-target requirements.
- Keep isolated wrappers where old ForgeGradle versions require them.
- Generate shared loader metadata and validation rules instead of copying them into 68 modules.
- Continue producing exact-Minecraft artifacts rather than risky cross-version universal JARs.

### 5. Port by API era

Use canary targets before filling each family:

1. Existing versions: implement protocol 6 and optional clients across the current 21 runtimes.
2. Legacy canaries: 1.12.2 Forge and 1.16.5 Fabric/Quilt/Forge.
3. Java 17 family: 1.18.2 and 1.19.2.
4. 1.20 canaries: 1.20, 1.20.4, and 1.20.5, covering old networking, stable modern networking, and the Java-21/custom-payload transition.
5. Fill remaining 1.20.x targets.
6. 1.21 canaries: 1.21, 1.21.2, 1.21.6, 1.21.9, and 1.21.11.
7. Fill the remaining 1.21.x targets.
8. Re-run 26.1.2 and 26.2 to prove the shared changes did not regress current releases.

Each canary must pass before its neighboring targets are cloned or adapted.

## Acceptance gates

Every one of the original 92 runtimes, plus every certified additive legacy runtime, must prove:

- A vanilla client joins, remains connected, reconnects, chats, and plays normally.
- No Jammarr payload, listener allocation, audio preparation, or Plex request is caused by that vanilla client.
- A matching client negotiates protocol 6 and receives normal UI, commands, state, and audio.
- A matching and vanilla client can coexist while music plays.
- An incompatible Jammarr client receives a clear protocol error.
- A modded client can join an unmodded server without disconnecting.
- Start, stop, reload, and disconnect leave no threads, ports, partial files, transfer state, or OpenAL resources behind.
- Loader metadata describes Jammarr as server-required/client-optional on distribution platforms.

All automated client GUI runs must use a fresh private X server, an isolated game directory, and an unset active Wayland display. The acceptance harness must never open windows on or send input to the active user's desktop session.

The modded-client-to-unmodded-server UI probe is now implemented in every distinct client-state source family. When the loader reports no Jammarr channel, the acceptance-only path opens the era-native Jammarr screen, requires the exact `This server does not support Jammarr` state to remain rendered across multiple ticks/frames, and emits one durable evidence marker without sending an unsupported payload. Source coverage finds all 14 state variants dynamically, and release compilation passed for Babric, the affected Forge/Fabric/Ornithe legacy targets, 1.12.2, 1.16.5, and every 26.1.2/26.2 loader after preserving their distinct screen APIs. A real unmodded-server runtime matrix remains required before this acceptance item can be checked.

`scripts/prepare-mojang-server.py` resolves exact vanilla server bytes, verifies metadata, size, JAR digest, readable ZIP structure, and absence of any Jammarr archive entry, then records explicit `unmoddedVanillaServer=true` and `jammarrPresent=false` attestations in a project-owned cache. All release versions use Mojang's SHA-1-addressed metadata directly. Mojang's current Beta 1.7.3 metadata omits its server download, so that one row uses the Babric manifest's pinned 503,100-byte Betacraft archival copy of the vanilla Beta server, with the accepted SHA-1 hard-coded and the non-Mojang provenance recorded rather than mislabeled. `scripts/run-unmodded-server-client-gate.sh <runtime>` boots only the attested server, launches the matching production modded client on private X with null audio, requires both an authoritative server join and the rendered unsupported-server UI marker, retains the connection for at least ten seconds, and verifies exact client/server/port cleanup. It shares the dedicated runtime lock so this reverse-compatibility test cannot perturb an audible or vanilla-client qualification. `scripts/run-unmodded-server-client-matrix.py` derives all 99 full runtimes from the manifest, preserves each attempt in its own directory, and resumes only after rehashing the attested JAR and rechecking provenance, join, UI, process, and closed-port evidence. Its verifier now recognizes both modern and legacy authoritative join formats and independently pins the Beta archival URL, size, SHA-1, source label, and Babric provenance URL while requiring official Mojang metadata/object URLs for release servers. All 29 distinct server versions have now been resolved and independently rehashed; live client execution remains pending behind the active two-hour qualification.

Reverse-matrix resume verification also reopens the selected server JAR as a readable ZIP and rejects every Jammarr-named entry instead of trusting the attestation's `jammarrPresent` flag alone. It binds each accepted row to the requested connected duration, requires schema-1 and well-formed current server/metadata digests, and records the exact target-manifest SHA-256 in aggregate evidence.

- Real-Plex validation on every Minecraft version and every loader-adapter family.
- Continue validating that only the selected Music library is exposed and that the separate ASMR library never appears in browse, search, shuffle, radio, or fallback results.

### Expanded legacy and cross-era certification

The legacy expansion increases testing rather than shifting coverage away from modern targets. CI must generate one independently runnable job per artifact/runtime from `gradle/targets.json`, run those jobs in parallel, and derive the release-gate total from the manifest. No final workflow, release script, or test harness may retain a fixed 17-, 68-, 75-, 92-, or 99-target assumption.

Every declared legacy artifact/runtime must pass these minimum gates:

- Reproducible clean build, dependency-lock verification, metadata inspection, bytecode/Java inspection, and canonical filename/checksum generation.

## Release sequence

- Release candidate artifacts go to DiscPanel first, with generated instances for the complete original 92-runtime matrix and every certified additive legacy runtime.
- Reconcile those instances from `gradle/targets.json` with `scripts/reconcile-discopanel-test-servers.py`. Its default mode is read-only; `--apply-native` creates missing native-loader instances sequentially, validates their final stopped state, disables immediate startup/autostart, and deliberately uploads no Jammarr artifact. `--apply-custom` handles only the manifest-declared Fabric-derived legacy profiles: Babric and Legacy Fabric use checksum-pinned versioned launchers, while Ornithe receives an inspected generation-2 bootstrap at the server root rather than a file in `mods/`. `--verify-custom-launchers` re-downloads and hashes every URL-based custom launcher without changing a server.
- Stage release candidates with `scripts/deploy-discopanel-release.py`. Its default mode verifies the complete release manifest, `SHA256SUMS`, local artifact bytes, server mapping, stopped/autostart-off state, and existing Jammarr records without mutation. Applying requires the explicit matching `--confirm-version`; each upload is rehashed from the remote `mods/` path before the prior active Jammarr record is disabled and retained as rollback. The deployer never starts or restarts a server and refuses duplicate active records or a partial prior deployment.
- Keep every server stopped with autostart disabled after automated certification.
- Preview-loader targets remain explicitly labeled beta until final user testing passes.
- Produce `manifest.json`, checksums, dependency metadata, and loader availability notes from the same target manifest.
- Publish Fabric files as both Fabric and Quilt compatible; never publish duplicate Quilt JARs.
- Update README language from “required on both sides” to “required on the server, optional on clients.”
- Only begin GitHub, CurseForge, and Modrinth publication after the full stable matrix and final user acceptance pass.
