# Release acceptance

The automated root gate is:

```bash
./gradlew releaseMatrixGate --no-daemon --max-workers=1
```

GitHub Actions runs the same release contract as 78 independent artifact jobs
with fail-fast disabled. Fabric artifact jobs also cover their matching Quilt,
Quilt with Mod Menu, and minimum-Fabric-Loader runtimes. The final `1.0 release
gate` job downloads all successful release artifacts, rebuilds the manifest and checksums,
and runs the centralized artifact inspector before publishing the candidate
bundle.

It must produce 75 JARs and three `.litemod` files plus schema-2 `manifest.json` and `SHA256SUMS` under `build/releases/`, then exercise 99 dedicated-server runtimes. These counts are derived from `gradle/targets.json` and must change with the manifest rather than being maintained independently. Run `sha256sum -c SHA256SUMS` from that directory before publication.

The release gate observes each real client's decoded output through an isolated audio sink; PLAYING state or an allocated OpenAL source alone is not accepted. Its deterministic carrier includes pseudo-random marker identities every 250 ms, and the retained JSON reports onset, marker displacement, marker-sequence mismatches, simultaneous-marker overlap, silence gaps, and inter-client skew. The oracle first proves that deliberately injected early, late, replayed, reordered, and overlapping PCM fail those checks. It also starts every modern Fabric artifact under Loader 0.19.2 as well as the pinned 0.19.3, and repeats all five Quilt client/audio scenarios with the pinned Mod Menu installed. Every clean two-client run must capture at least ten seconds with no post-start silence gap over 60 ms, marker displacement over 40 ms, marker-sequence mismatch count over two, simultaneous-marker overlap over 20 ms, onset over 300 ms (one 250 ms marker period plus the analysis window), or inter-client skew over 150 ms. Run `scripts/run-audio-impairment-matrix.sh` for the representative 1.7.10 Forge plus 1.20.1 and 26.2 Fabric, Quilt, Forge, and NeoForge targets. Retain all six profiles: direct, fixed 150 ms latency, 20–250 ms jitter, one two-second stall, repeated 250 ms client stalls, and six seconds below the configured stream bitrate.

Multi-window and churn runs must additionally pass `scripts/audit-shared-clock-continuity.py`. The continuity audit correlates each capture's complete 10 ms pseudo-random marker-identity envelope, rather than matching only the binary marker type within one window, and rejects a relative-lag step over 40 ms even when the windows on either side independently remain below the 150 ms skew ceiling. When bounded pre-backend feeds are supplied, an intact feed pair plus a rendered-only lag step is classified as a rendered-backend phase shift; it is still a failed release result, not permission to relax the timing limits.

Minecraft 1.16.5-and-newer clients must also exercise the OpenAL heard-position clock when `AL_SOFT_source_latency` is available. The player tracks whole PCM frames submitted by each streaming buffer, maps the backend's queued-buffer count to those submissions, and calculates heard position after queue offset and device latency. A cold backend remains muted while its first source establishes latency; the learned lead survives ordinary stop, track, and sound-reload boundaries. Runtime acceptance requires two same-direction measurements beyond 40 ms before automatic recovery, while an unavailable extension, inaccessible source field, partial PCM frame, or impossible queue measurement must fail closed to the existing 500 ms wall-clock policy. The deterministic drift scenario must log the injected displacement, two backend-clock measurements, `backend playback drift` recovery, resumed audible output, and clean teardown before the two-second wall-clock fallback could be responsible. The 2026-09-01 private-X 1.20.1 Fabric canary measured 135-172 ms device latency, held steady-state drift between -30 and 20 ms, recovered an injected 2,502 ms displacement through the backend path, passed its complete two-client audible scenario suite with zero rendered skew, sequence errors, overlap, or silence, and left no process or port. The separately mapped 1.16.5 Fabric canary passed the same full scenario suite and backend-first 2,496 ms recovery at -18 through 2 ms steady drift; the Forge direct canary independently exercised its `SoundSource` field mapping and rendered 10.9 seconds with zero skew, sequence errors, overlap, or silence before clean teardown.

Forge 1.7.10 additionally runs `scripts/run-forge1710-regression-gate.sh`. Its core phase uses the final reobfuscated JAR for persistence, a 30-minute fixture, twenty cold clients, two sound reloads per client, lifecycle transitions, pending-browse disconnect cleanup, the LiteLoader companion, and optional-client negotiation. Its impairment phase repeats sustained two-client output under all six network profiles. Direct, scenario, and audible gates hold the repository-wide runtime lock exclusively because different evidence directories can still share production game directories, ports, and measured host resources. If the server or either client disconnects during a deterministic capture, the gate reports an infrastructure interruption and refuses to misclassify the recorder's trailing silence as an audio-timing failure.

The non-audio artifact-free-client and modded-client-to-vanilla-server matrices may use `scripts/run-compatibility-matrix-shards.py --jobs 4`. For release qualification, also pass `--output-suffix candidate-<short-commit>` and a matching fresh `--shard-root`; the safe suffix creates distinct canonical evidence roots for both matrices, is recorded in the dry-run plan, and prevents `--resume` from accepting rows produced by an older candidate with the same product version. Each shard holds the global runtime lock in shared mode and an exclusive lock keyed to its Minecraft/cache family; every loader for one Minecraft version therefore stays in one lane, including Fabric/Quilt workspace aliases, while independent versions can run concurrently. The project-owned vanilla-client cache uses per-destination advisory locks and atomic replacement for metadata, libraries, natives, indexes, and asset objects. A failed or interrupted shard signals its active matrix, waits for that gate's bounded cleanup, and stops the remaining lanes. Only a final full-manifest `--resume --verify-only` pass against those candidate-specific roots may write the canonical 91- or 99-profile summary, so shard success cannot conceal missing, stale, running-process, or open-port evidence.
